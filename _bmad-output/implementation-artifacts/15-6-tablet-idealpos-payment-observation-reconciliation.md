## What was built

### Backend (`apps/api/src/payment-observation/`)

A domain **deliberately separate** from `POSSyncRecord` (order-submission reconciliation, Story 15-5) — payment observation is a distinct, later lifecycle leg, and coupling the two would let submission/kitchen-delivery activity be mistaken for payment evidence.

- **Schema** (migration `20260821011551_payment_observation`, purely additive): `PaymentObservationState` enum (`not_observed`/`observation_unsupported`/`pending`/`paid`/`declined`/`cancelled`/`reversed`/`refunded`/`uncertain`/`conflict`); `PaymentObservationSourceKind` (`fixture`/`connector`); `PaymentObservation` (one row per order, **lazily created on first observation — never eagerly backfilled**, since absence already honestly means `not_observed`/`observation_unsupported`); `PaymentObservationEvent` (append-only, immutable raw-fact ledger — the actual "immutable recording of raw observed facts and provenance" this story's own bar requires). `nativeReference` is DB-unique (nulls unrestricted, mirroring `Order.paymentProviderTransactionId`'s own precedent) — one native reference can never silently attach to two orders. `(orderId, observationId)` is DB-unique on the event table — the caller-supplied idempotency key. Reuses `IdealposEvidenceTier` directly (no parallel enum) and `POSAdapterType` for provenance.
- **`payment-observation.constants.ts`**: an explicit, closed `PAYMENT_OBSERVATION_ALLOWED_TRANSITIONS` table — the sole authority for whether an incoming observation may change state. `declined`/`cancelled`/`reversed`/`refunded`/`conflict` are dead ends; nothing may automatically leave them. Any transition not listed is redirected to `conflict`, never silently applied — this is what makes "out-of-order updates cannot regress a terminal state" true by construction, not by trusting a client timestamp.
- **`dto/payment-observation-event.dto.ts`**: a strict, fail-closed parser (`parsePaymentObservationEvent`) mirroring `idealpos-order-result.dto.ts`'s own discipline exactly — unsupported schema version, unknown state, malformed timestamp, or an amount without a currency are all rejected explicitly.
- **`payment-observation.service.ts`**: `recordObservation` — durably inserts the raw event FIRST (immutable), then applies it to the projection via a bounded-retry (5 attempts) database compare-and-set, exactly mirroring `IdealposOrderReconciliationService.transitionTerminal`'s proven CAS pattern. A duplicate `(orderId, observationId)` with an **identical** payload (fingerprinted via SHA-256) is a safe no-op; a **different** payload for the same id fails closed with `ConflictException`. Reconciliation is computed only when transitioning into `paid`/`reversed`/`refunded`, and only when both currency and amount are proven — classified `exact_match`/`mismatch`/`missing_native_amount`/`currency_mismatch`, never auto-corrected. `recordUnverifiedAmount` mirrors `recordUnverifiedTableAmount`'s own pattern — never touches `state`/`nativeAmountCents`. `acknowledge` (idempotent) only ever writes `reviewedAt`/`reviewedByStaffId`/`reviewNote` — it can never change native payment truth.
- **`payment-observation.controller.ts`**: `GET /admin/venues/:id/payment-observations`, `GET /admin/orders/:id/payment-observation`, `POST /admin/payment-observations/:id/acknowledge`. Every route explicitly rejects **any** `tablet_device`/`tablet_staff`/`tablet_manager`/`kds_device` identity **regardless of the StaffRole an elevation carries** (a PIN-elevated tablet token can carry a real `cashier`/`manager` role, which a role-only `RolesGuard` check would otherwise admit) — "prefer no payment UI on the tablet" is enforced at the API boundary, not just by omission in the frontend. View: `admin`/`manager`/`cashier`. Acknowledge: `admin`/`manager` only.
- **`payment-observation-fixture-injection.controller.ts`**: `POST /admin/payment-observation-fixtures/orders/:orderId/inject-observation` — the only real writer of a `PaymentObservationEvent` in this repository today. Fail-closed, defense in depth: `NODE_ENV !== 'production'` checked first, then staff auth + `admin`/`manager` role, then an explicit device-identity rejection. Every event this endpoint creates is stamped `evidenceTier: fixture_contract` (the column default); nothing here can set `real_windows_table12`/`real_production`.

### Admin Console (`apps/admin-console/src/pages/payments/PaymentsPage.tsx`)

**Replaced entirely.** The prior page was ~1300 lines of fabricated sample data — fake Stripe/EFTPOS terminal fleet, fake settlements, a "New Refund" action, 24 invented transaction rows — none of it backed by anything this system does. It violated this story's own required UX bar outright (fake sample values, implied Card/Cash/Refund controls). Replaced with a real, API-backed, venue-scoped table: order, service mode/table/takeaway reference, status badge (never "Paid" without authoritative evidence — `observation_unsupported`/`not_observed` are visually and textually distinct from `paid`), provisional vs. native amount (unverified amounts explicitly labelled, never conflated with the authoritative figure), native reference, tender, discrepancy classification, last-observed time, and a manager/admin-only "Mark reviewed" action for `conflict` rows. Loading/empty/error states; a fixed banner stating the payment/observation boundary; state-filter chips; zero Card/Cash/Pay/Charge/Refund/Void controls (grep-verified). Refresh re-fetches, never mutates.

**Design note, recorded not hidden:** `listForVenue` (and the list-view table) shows only orders that already have a `PaymentObservation` row — it does not synthesize an `observation_unsupported` row for every historical order lacking one (unlike the single-order `getForOrder` read, which does synthesize the honest default). This is a deliberate operational-usefulness choice (a list of hundreds of "unsupported" rows for every pre-existing order would be noise, not signal); the per-order detail path (`GET .../orders/:id/payment-observation`) remains honest for any individual order regardless of whether a row exists.
