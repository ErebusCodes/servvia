# Story 15.4: Idempotent Submission and Truthful Provisional Totals

Status: done

## Story

As the platform operator running the Order Tablet at the single Dunedin production venue,
I want the tablet's on-screen provisional total to be a truthful, GST-inclusive, non-fabricated figure, and every order submission to be idempotent,
so that staff and guests never see or send a fictitious charge before Idealpos exists to authorize the real one (Story 15-5).

## Scope (per this session's governing brief)

This story owns the tablet's **Verdura-side provisional billing calculation** — removing the fabricated 10% service charge, correcting the additive-GST bug per DL-072, disclosing contained GST without adding it, keeping whole-table/per-seat totals internally consistent, and failing safely for an unsupported venue tax configuration. It also completes the canonical `epics.md` E15-S4 scope's idempotency-key half (see Dev Agent Record — a real, severed submission path, not merely a style gap).

It explicitly does **not** implement: Idealpos submission/authoritative totals (15-5), EFTPOS/cash payment confirmation (15-6), reconciliation/audit views (15-10), the tablet auth-identity decision (15-1, still blocked), Print Bill's backend wiring or KOT dispatch (8-1/E8-S1), or a configurable service-charge/promotion/multi-jurisdiction tax system (explicitly out of scope — see brief).

## Acceptance Criteria

1. The automatic 10% service charge is removed from every calculation and every display site on the canonical Order Tablet (`apps/admin-console/src/pages/order-tablet/OrderTabletPage.tsx`) — not replaced with another fee, not restored on reload.
2. For a GST-inclusive amount: subtotal/payable before discount is the sum of GST-inclusive item/modifier prices; contained GST is `gross × 3 / 23`, disclosed but never added to the payable total.
3. A valid discount (the existing `VERDURA10` toggle) reduces the taxable/payable base and its disclosed GST consistently, can never produce a negative payable amount, and — per the brief's ownership-boundary instruction — is not itself re-authorized or turned into a new promotion system in this story.
4. Whole-table and per-seat totals (subtotal, payable, contained GST) are internally consistent and reconcile under a documented, tested rounding rule (largest-remainder allocation — see `billing.ts`) rather than leaving an unexplained penny gap between the sum of seat figures and the table figure.
5. The real venue tax configuration (`currency`/`taxJurisdiction`/`pricesIncludeTax`) is read from the actual `Venue` record, not hardcoded; an unsupported/unreadable configuration fails safely (totals hidden, a clear message shown, charging disabled) rather than silently applying NZ GST rules to an incompatible venue.
6. The provisional total is visibly labelled as provisional/pending-Idealpos-confirmation everywhere it is prominently shown, and nothing in this story's changes implies Idealpos acceptance, an EFTPOS charge, or payment completion.
7. Order-affecting behaviour (table/seat/course/modifier/quantity/notes selection, KDS presentation, navigation, the existing auth gate) is unchanged; order submission is truly idempotent (see Dev Agent Record — this closes a real, previously-broken gap, not a hypothetical one).
8. Focused, deterministic automated coverage exists with explicit expected-cents assertions, including a regression test that fails under the old (10%-service + additive-15%-GST) formula.
9. Real-browser verification confirms the above against the live dev stack, not mocks alone.

### Implementation

**New calculation module — `apps/admin-console/src/pages/order-tablet/billing.ts`.** The single deterministic calculation boundary for the tablet's totals, replacing the previous component-local float-dollar arithmetic. Computes internally in integer cents (`dollarsToCents` rounds once at the boundary, avoiding accumulated float drift from `TabletCartItem`'s pre-existing dollar convention and from `priceDeltaCents / 100` modifier deltas). Exposes `computeCartTotals(lines, discount)` returning `{ subtotalCents, discountCents, payableCents, containedGstCents, seatBreakdown[] }` — no service charge field exists anywhere in this shape. `containedGstCents` implements DL-072's `gross × 3 / 23` extraction, disclosure-only, never added to `payableCents`. `allocateByLargestRemainder` reconciles per-seat discount/GST shares to sum exactly to the table-level rounded figures (the largest-remainder method — deterministic, tie-broken by input order) rather than leaving naive independently-rounded per-seat figures off by a cent. `isSupportedTaxProfile`/`SUPPORTED_TAX_PROFILE` gate all of this on the real NZ GST-inclusive venue profile — a venue configuration outside that profile is explicitly not calculated, not silently miscalculated.

**`OrderTabletPage.tsx` integration.** `totals` (the pre-existing object every display site already read from) is now derived from `computeCartTotals` — `totals.sub`/`totals.total` unchanged in shape/unit (dollars) so no downstream consumer needed to change; `totals.service` no longer exists (grep-confirmed zero remaining references); `totals.gst` is now the disclosed, non-added contained-GST figure. `seatSubtotal`/`seatGrand` now read directly from `cartTotals.seatBreakdown` via `seatBreakdownFor` (single source of truth — no separate ratio-based per-seat calculation left in the component). Added a `venueTaxProfile`/`taxProfileStatus` state pair, populated by a new `GET /api/venues/:id/tax-config` fetch (see Backend below) on mount; `taxConfigUnavailable` (`status==='error'` or a `ready` status with an unsupported profile) disables the Charge/Place-order and Pay buttons and replaces the Total row with a clear "Unable to calculate a safe total for this venue's tax configuration" message, in the order-screen aside and the payment-screen aside — "Send to kitchen" (kitchen prep) is deliberately left unaffected by this gate, since it doesn't depend on billing correctness; this is a documented scope decision, not an oversight. Added a "Provisional — pending Idealpos confirmation" caption beside every prominent Total display (order aside, payment aside, enquiry dialog, print-bill TOTAL line) — text-only, no behavioural change, satisfying AC6 without touching Story 15-6's payment-completion mechanism (`handlePayAll`/"Payment complete" screen are untouched, exactly as instructed — that fix belongs to 15-6).

Every "Service charge (10%)"/"Service 10%" row was removed outright (not zeroed, not hidden via a flag) from: the order-screen aside, the payment-screen aside, the enquiry-dialog footer (`feesStr` → `gstStr`, GST-only), and the print-bill dialog. Every "GST (15%)"/"GST 15%" label was relabelled "GST included" to reflect that it is now disclosure of a contained amount, not an additive line — same value slot, corrected meaning.

**Idempotent submission (closing the found 400 defect).** Added `orderIdempotencyKey` state (`crypto.randomUUID()`, generated once per table's order-in-progress, reused across retry attempts for that same logical order, rotated in `handleReset` when a genuinely new order starts) and included it in `submitOrderToKitchen`'s POST body. This is the idempotency-key half of `docs/epics.md`'s canonical E15-S4 scope, completed here because the defect it was meant to prevent (a missing key) turned out to already be causing a hard failure, not a latent risk.

**Backend — `GET /api/venues/:id/tax-config` (new, minimal).** `docs/epics.md`'s Story 15-4/DL-072 text requires the tablet to "use the real venue tax configuration where Story 15-4 requires it... do not silently hardcode NZ assumptions if the existing implementation exposes [currency/locale/taxJurisdiction/pricesIncludeTax]." The existing implementation exposed nothing to the tablet (`GET /api/venues/:id` returns the full `Venue` record — address, `posConfig`, etc. — and is `admin`/`manager`-only, which a standalone `kds_device` token, role `kitchen`, cannot call). Rather than broaden the full-record endpoint's exposure, added a narrow, org-scoped, `admin`/`manager`/`kitchen`-accessible endpoint (`VenuesService.getTaxConfig`, `VenuesController`) returning only the four low-sensitivity tax/currency fields — reusing the exact RBAC pattern the sibling `venues/:venueId/tables` endpoint already established for the same `kds_device`-vs-JWT tablet-access problem, not inventing a new authorization policy.

### Defect found, reproduced, and deliberately NOT fixed (outside this story's boundary)

**Modifier price deltas are silently dropped to $0 by the backend for any modifier not present in the real `MenuItem.modifierGroups` catalog — confirmed live, real order evidence attached.** During Runtime Validation, adding "Verdura Mezze Board" ($70.00) with the "Toum Garlic Paste" (+$0.50) modifier correctly showed **$70.50** on the tablet (subtotal, GST-included, and total all consistent) — but the real persisted order (`ORD-600001`, queried directly from Postgres) recorded `unitPriceCents: 7000`, `lineTotalCents: 7000`, and `selectedModifiers: [{ "name": "Toum Garlic Paste", "priceDeltaCents": 0 }]` — i.e. the backend silently priced the modifier at **$0.00**, a **$0.50 discrepancy** between what staff saw and what was actually stored/would be charged.

Root cause (read, not modified): `OrdersService.resolveModifiers` (`apps/api/src/orders/orders.service.ts:1002-1027`) builds its price catalog from the target `MenuItem`'s own `modifierGroups` JSON column and explicitly ignores any client-supplied `priceDeltaCents` for names it doesn't recognize — correct, safe, security-conscious backend behaviour (never trust a client-asserted price). The actual defect is upstream: the Order Tablet's entire modifier catalog (`getModifierGroupsForItem`, `OrderTabletPage.tsx`) is a **client-side, category-name-substring-matched fiction** with no relationship to any real `MenuItem.modifierGroups` data — which is exactly and only the gap `docs/epics.md` E15-S3 ("Menu and modifier integrity") already names as its own scope ("Replace `getModifierGroupsForItem`'s hardcoded category-substring-matched modifiers with real `MenuItem`/modifier-group configuration"). Fixing it requires populating real per-item modifier-group data and rewriting the tablet's modifier catalog to read it — a menu-configuration-integrity change, not a tax/service-charge arithmetic one, and squarely owned by E15-S3, not 15-4.

**Not fixed here, per the brief's own defect-handling rule** ("do not expand the implementation... record it separately with severity, evidence, impact and recommended owner"). Recorded in `deferred-work.md` below with this exact reproduction. **Severity: P0** — this is a real, live, staff-facing-vs-charged-amount billing discrepancy, materially the same class of concern this story exists to close, just one level deeper (backend modifier pricing rather than tablet-side service-charge/GST arithmetic). **Impact:** any order with a non-zero-delta modifier the backend's `MenuItem.modifierGroups` doesn't recognize is stored (and would be submitted to Idealpos once 15-5 exists) at a lower price than the tablet displayed to staff/guest. **Recommended owner: E15-S3.**
