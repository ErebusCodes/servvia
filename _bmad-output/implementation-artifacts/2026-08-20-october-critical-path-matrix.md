## 2a. GST reconciliation fix and non-SSH verification completion (same-day follow-on session)

**Root cause found and fixed:** `OrdersService.computeTotals` (`apps/api/src/orders/orders.service.ts`) added an additive 15% GST on top of already GST-inclusive menu prices — the exact convention DL-072 (2026-08-17) already ruled incorrect for the tablet's own `billing.ts`, but `computeTotals` itself was explicitly *not* fixed at that time (DL-072's own text: "This decision does not fix `computeTotals`... flagged here as a materially significant, currently-unowned finding"). Because `POSSyncRecord.provisionalPayableCents` is a direct copy of `computeTotals`'s output (`persistOrder`, same file), every Story 15-5 reconciliation comparison was checking Idealpos's correct authoritative total against a provisional total that was ~15% too high — a **false discrepancy**, not a real one, on every order. `$70.00` persisted as `$80.50` before this fix.

**Correction:** `computeTotals` now takes the venue and, for the one supported tax profile (`NZD`/`NZ_GST`/`pricesIncludeTax: true`, mirroring `billing.ts`'s `SUPPORTED_TAX_PROFILE`), returns `totalCents = subtotalCents` (no addition) with `taxCents` as the disclosed contained-GST component (`round(subtotalCents × 3 / 23)`). An unsupported/unrecognized tax profile now fails closed (`UnprocessableEntityException`) rather than guessing. The check is deliberately deferred until *after* the idempotent-replay check in both `create()` and `createStaffOrder()` — a bug found and fixed during this same review: computing totals unconditionally would have let a later tax-config problem block a legitimate replay of an already-accepted order, which must never happen.

**Three further real defects found and fixed during the resulting local-browser walkthrough** (all in `apps/admin-console/src/pages/order-tablet/OrderTabletPage.tsx`, all pre-existing, none introduced by the GST fix):

1. **Cross-table stale reconciliation display (billing-safety, the most serious of the three).** `createdOrderRef` (which order's Idealpos status to poll/display) was only ever re-derived when it was already `null`. Once any table's payment screen had been viewed, switching to a *different* table's payment screen kept polling and displaying the *first* table's reconciliation status. Reproduced live: Table 2 had a real, unresolved $4.00 discrepancy in the database, but the payment screen showed Table 1's "Idealpos confirmed — totals match" and enabled the Pay button — a table with a genuine unresolved discrepancy could have been charged as if it matched. Fixed: the resync effect now always re-derives `createdOrderRef` from the live orders query for whichever table is currently selected (clearing to `null`, not stale, if that table has no order yet), and the polling effect now clears the displayed panel immediately on every `createdOrderRef` change so no stale cross-order data can render even momentarily.
2. **Idempotency key never rotated across tables.** `orderIdempotencyKey` was only rotated by `handleReset` (reachable only after a full payment cycle at the same table). Starting a second order at a *different* table while an earlier order was still open (ordinary concurrent-table service) reused the stale key; the backend correctly rejected the second submission with a confusing "idempotencyKey already used for a different order" error, silently blocking normal multi-table service. Reproduced live (table 5's submission failed after table 4's had already used the key). Fixed: the key now rotates whenever a genuinely new (non-occupied-table) order is started.
3. **`hydrateTableOrder` crashed re-opening a just-created order.** `OrdersService.persistOrder`'s transaction returned the bare `Order` row (no `items` relation loaded) as the immediate `POST /admin/orders`/`kiosk/orders` response — the one order-serving shape inconsistent with `findAll`/`findOne`/the WebSocket push, which all correctly include `items`. The Order Tablet frontend caches that immediate response and later re-hydrates a re-opened table's cart from it; re-opening a table within the (usually short, non-zero) window before the next list refetch/WebSocket reconciliation caused a real `TypeError: Cannot read properties of undefined (reading 'map')`, reproduced live in the browser console, aborting the table-selection handler partway through. Fixed at the root (`persistOrder` now returns the order with `items` included, matching every other order-serving path) plus a defensive `order.items ?? []` guard in `hydrateTableOrder` itself.

Regression tests added for all four defects (GST math, tax-profile fail-closed, replay-not-blocked-by-tax-config, cross-table reconciliation display — proven via a real Postgres end-to-end order created through the real HTTP API, not a hand-set fixture — idempotency-key rotation). Full test/build/lint evidence in the Story 15-5 implementation record.
